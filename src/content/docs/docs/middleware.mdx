Genkit allows you to use middleware to modify the behavior of `generate()` calls. Middleware can be used for various purposes, such as retrying failed requests, falling back to different models, or injecting tools and context.

You can use pre-packaged middleware or build your own custom middleware.

<Lang lang="js">

The official Genkit middleware for JavaScript is available in the `@genkit-ai/middleware` package.

## Installation

```bash
npm install @genkit-ai/middleware
# or
yarn add @genkit-ai/middleware
# or
pnpm add @genkit-ai/middleware
```

## Available middleware

The `@genkit-ai/middleware` package provides several useful middleware options out of the box. This list represents the middleware built and maintained by the Genkit team, but there may also be community-built middleware available.

### 1. FileSystem middleware (`filesystem`)

Grants the model access to the local filesystem by injecting standard file manipulation tools (`list_files`, `read_file`, `write_file`, `search_and_replace`). All operations are safely restricted to a specified root directory.

```typescript
import { genkit } from 'genkit';
import { filesystem } from '@genkit-ai/middleware';

const ai = genkit({ ... });

const response = await ai.generate({
  model: googleAI.model('gemini-flash-latest'),
  prompt: 'Create a hello world node app in the workspace',
  use: [
    filesystem({ rootDirectory: './workspace' })
  ]
});
```

**Configuration options:**

- `rootDirectory` (required): The root directory to which all filesystem operations are restricted.
- `allowWriteAccess` (optional): If true, allows write access to the filesystem (defaults to `false`).
- `toolNamePrefix` (optional): Prefix to add to the name of the injected tools.

### 2. Skills middleware (`skills`)

Automatically scans a directory for `SKILL.md` files (and their YAML frontmatter) and injects them into the system prompt. It also provides a `use_skill` tool the model can use to retrieve more specific skills on demand.

```typescript
import { genkit } from 'genkit';
import { skills } from '@genkit-ai/middleware';

const ai = genkit({ ... });

const response = await ai.generate({
  prompt: 'How do I run tests in this repo?',
  use: [
    skills({ skillPaths: ['./skills'] })
  ]
});
```

### 3. Tool approval middleware (`toolApproval`)

Restricts execution of tools to an approved list. If the model attempts to call an unapproved tool, it throws a `ToolInterruptError` allowing you to prompt the user for manual confirmation before resuming.

```typescript
import { genkit, restartTool } from 'genkit';
import { toolApproval } from '@genkit-ai/middleware';

const ai = genkit({ ... });

// 1. Initial attempt
const response = await ai.generate({
  prompt: 'write a file',
  tools: [writeFileTool],
  use: [
    toolApproval({ approved: [] }) // Empty list means call triggers interrupt
  ]
});

if (response.finishReason === 'interrupted') {
  const interrupt = response.interrupts[0];

  // 2. Ask user for approval, then recreate the tool request with approval
  const approvedPart = restartTool(interrupt, { toolApproved: true });

  // 3. Resume execution
  const resumedResponse = await ai.generate({
    messages: response.messages,
    resume: { restart: [approvedPart] },
    use: [
      toolApproval({ approved: [] })
    ]
  });
}
```

### 4. Retry middleware (`retry`)

Automatically retries failed model generations on transient error codes (like `RESOURCE_EXHAUSTED`, `UNAVAILABLE`) using exponential backoff with jitter.

```typescript
import { genkit } from 'genkit';
import { retry } from '@genkit-ai/middleware';

const ai = genkit({ ... });

const response = await ai.generate({
  model: googleAI.model('gemini-pro-latest'),
  prompt: 'Heavy reasoning task...',
  use: [
    retry({
      maxRetries: 3,
      initialDelayMs: 1000,
      backoffFactor: 2
    })
  ]
});
```

**Configuration options:**

- `maxRetries` (optional): The maximum number of times to retry a failed request (default: 3).
- `statuses` (optional): An array of `StatusName` values that should trigger a retry (default: `['UNAVAILABLE', 'DEADLINE_EXCEEDED', 'RESOURCE_EXHAUSTED', 'ABORTED', 'INTERNAL']`).
- `initialDelayMs` (optional): The initial delay between retries in milliseconds (default: 1000).
- `maxDelayMs` (optional): The maximum delay between retries in milliseconds (default: 60000).
- `backoffFactor` (optional): The factor by which the delay increases after each retry (exponential backoff, default: 2).
- `noJitter` (optional): Whether to disable jitter on the delay (default: false).

### 5. Fallback middleware (`fallback`)

Automatically switches to a different model if the primary model fails on a specific set of error codes. Useful for falling back to a smaller/faster model when a large model exceeds quota limits.

```typescript
import { genkit } from 'genkit';
import { fallback } from '@genkit-ai/middleware';

const ai = genkit({ ... });

const response = await ai.generate({
  model: googleAI.model('gemini-pro-latest'),
  prompt: 'Try the pro model first...',
  use: [
    fallback({
      models: [googleAI.model('gemini-flash-latest')], // try flash if pro fails
      statuses: ['RESOURCE_EXHAUSTED']
    })
  ]
});
```

**Configuration options:**

- `models` (required): An array of model references to try in order.
- `statuses` (optional): An array of `StatusName` values that should trigger a fallback (default: `['UNAVAILABLE', 'DEADLINE_EXCEEDED', 'RESOURCE_EXHAUSTED', 'ABORTED', 'INTERNAL', 'NOT_FOUND', 'UNIMPLEMENTED']`).
- `isolateConfig` (optional): If true, the fallback model will not inherit the original request's configuration (default: false).

### 6. Agents middleware (`agents`)

Lets an orchestrator delegate to sub-agents. It adds one `delegate_to_<agent>` tool per configured agent and lists the agents in the system prompt. The `continue_task` tool picks up failed, aborted, or finished tasks of sub-agents that have a session store. With `async: true`, delegations can also run in the background.

```typescript
import { agents } from '@genkit-ai/middleware';

const orchestrator = ai.defineAgent({
  name: 'orchestrator',
  system: 'Delegate research to the researcher and coding to the coder.',
  use: [agents({ agents: ['researcher', 'coder'], async: true })],
});
```

See [Multi-agent delegation](/docs/agents/multi-agent) for the options, background delegation, and task continuation.

### 7. Artifacts middleware (`artifacts`)

Gives the model `read_artifact` and `write_artifact` tools over the session's artifacts, and lists the current artifacts in the system prompt each turn. Pass `readonly: true` to provide only `read_artifact`, for example on an orchestrator that reads what its sub-agents produced.

```typescript
import { artifacts } from '@genkit-ai/middleware';

const builder = ai.defineAgent({
  name: 'builder',
  system: 'You are a code generator. Use write_artifact to create files.',
  use: [artifacts()],
});
```

### 8. Context compression middleware (`contextCompression`)

Keeps a conversation inside a token budget through long chats and tool loops. When the context grows past `maxInputTokens`, the middleware compresses what the model receives, cheapest strategy first, while the history you get back keeps every message.

```typescript
import { genkit } from 'genkit';
import { contextCompression, resolveCompressedHistory } from '@genkit-ai/middleware';

const ai = genkit({ ... });

const response = await ai.generate({
  model: googleAI.model('gemini-flash-latest'),
  prompt: 'Research this topic thoroughly.',
  tools: [searchTool],
  use: [
    contextCompression({
      maxInputTokens: 80000,
      deduplicateToolResponses: { matchBy: 'name-and-input' },
      toolResponses: { maxChars: 2000, preserveRecent: 2 },
      summarize: {
        model: googleAI.model('gemini-flash-lite-latest'),
        preserveRecent: 6,
      },
    }),
  ],
});

// The full transcript, with compression state in message metadata:
console.log(response.messages.length);

// The messages the model actually received:
const active = resolveCompressedHistory(response.messages);
```

Compression runs when the estimated tokens, or the input tokens the model reported for the previous call, exceed `maxInputTokens`, or when the conversation holds more than `maxMessages` messages. The strategies run in order:

1. `deduplicateToolResponses` replaces older duplicate tool responses with a short notice.
2. `toolResponses` truncates older tool responses, leaving the newest tool messages intact. The same pass cuts any single tool response over `maxToolResponseChars` with a `[TRUNCATED: ...]` marker. That cap applies on every turn, whether or not compression is triggered.
3. `summarize` has a model fold older messages into a summary, sized so that the system messages, the summary, and the kept messages fit within `maxMessages`. It is skipped when the cheaper strategies already saved `skipSummarizationThreshold` of the context and brought it under budget.
4. Only if nothing was summarized, older non-system messages are dropped, keeping the history starting on a user turn: down to `maxMessages`, or down to `preserveRecent` if the context is still over budget. By default a notice tells the model that context was removed.

**The model gets a view, the history keeps the transcript.** By default (`preserveOriginalMessages: true`), compression state is recorded in message metadata under `contextCompression` rather than replacing messages. Later turns build on earlier compactions, so compression carries across `generate()` calls and agent sessions as long as you pass the history forward. A history that the Go middleware compressed resolves the same way.

**Order.** List `contextCompression` after middleware that adds context (`filesystem`, `skills`, `artifacts`, `agents`) so it accounts for what they add.

**Configuration options:**

- `maxInputTokens` (optional): Compress when the context exceeds this many tokens (default: `Infinity`).
- `maxMessages` (optional): Compress when the conversation holds more than this many messages, and trim it back to this many. The newest turn is always kept, even when the system messages and the truncation notice already fill the cap.
- `preserveRecent` (optional): How many of the newest non-system messages are kept when older ones are dropped, and the default window for `summarize` (default: 4).
- `preserveSystem` (optional): Always keep system messages (default: `true`).
- `maxToolResponseChars` (optional): Hard cap on the characters of any one tool response, applied on every turn (default: 400000). `<= 0` or `Infinity` disables it.
- `deduplicateToolResponses` (optional): `matchBy` is `'name-and-input'` (default) or `'name-only'`; `keepRecent` is how many of the newest responses per group stay intact (default: 1); `notice` replaces the default notice.
- `toolResponses` (optional): `maxChars` is the most characters an older tool response keeps; `preserveRecent` is how many of the newest tool messages stay intact (default: 2).
- `summarize` (optional): `model` (required) writes the summaries; `preserveRecent` is how many of the newest messages stay out of the summary (default: the top-level `preserveRecent` when set, 6 otherwise); `prompt` replaces the default prompt, with `{conversation}` standing in for the messages to summarize.
- `skipSummarizationThreshold` (optional): Skip `summarize` when the cheaper strategies saved at least this fraction (`0..1`) of the context and brought it under `maxInputTokens`.
- `insertTruncationNotice` / `truncationNotice` (optional): Whether to insert a notice when messages are dropped (default: `true`), and its text.
- `preserveOriginalMessages` (optional): Keep the original messages in `request.messages` and `response.messages` (default: `true`). Set to `false` to overwrite them with the compressed view.

## Building your own custom middleware

You can implement your own custom middleware to extend Genkit's functionality. Genkit provides a `generateMiddleware` helper to create structured middleware with configuration schemas.

Middleware can intercept different phases of execution by providing hooks:

- `model`: Intercepts the call to the model.
- `tool`: Intercepts tool execution.
- `generate`: Intercepts the high-level generation loop.

Here is an example of a custom middleware that logs requests and responses:

```typescript
import { generateMiddleware, z } from 'genkit';

export const loggerMiddleware = generateMiddleware(
  {
    name: 'loggerMiddleware',
    description: 'Logs requests and responses',
    configSchema: z.object({
      verbose: z.boolean().optional(),
    }),
  },
  ({ config, ai }) => {
    return {
      model: async (req, ctx, next) => {
        if (config?.verbose) {
          console.log('Request:', JSON.stringify(req));
        }
        const resp = await next(req, ctx);
        if (config?.verbose) {
          console.log('Response:', JSON.stringify(resp));
        }
        return resp;
      },
    };
  },
);
```

To use it:

```typescript
const response = await ai.generate({
  model: googleAI.model('gemini-flash-latest'),
  prompt: 'Hello',
  use: [loggerMiddleware({ verbose: true })],
});
```

For more complex examples of building custom middleware, you can refer to the source code of the built-in middleware in the [Genkit GitHub repository](https://github.com/genkit-ai/genkit/tree/main/js/plugins/middleware).

## Installation

The middleware framework is part of the core `ai` package, and the pre-packaged middleware ships in `plugins/middleware`. Both come with the core Genkit module:

```bash
go get github.com/firebase/genkit/go@latest
```

Register the `Middleware` plugin during `genkit.Init` to expose the built-ins to the Dev UI and to other-runtime callers:

```go
import (
    "context"

    "github.com/firebase/genkit/go/genkit"
    "github.com/firebase/genkit/go/plugins/googlegenai"
    "github.com/firebase/genkit/go/plugins/middleware"
)

ctx := context.Background()
g := genkit.Init(ctx, genkit.WithPlugins(
    &googlegenai.GoogleAI{},
    &middleware.Middleware{},
))
```

The snippets that follow also draw on `errors`, `log`, `net/http`, `os`, `time`, `github.com/firebase/genkit/go/ai`, and `github.com/firebase/genkit/go/core/status`.

For pure Go programs that just attach middleware to a `genkit.Generate()` call, plugin registration is optional. Passing a middleware value directly to `ai.WithUse` invokes its `New` method on the local fast path without consulting the registry.

## Attaching middleware

`ai.WithUse` is the option that attaches middleware. It returns an `ai.CommonGenOption`, so the same call is accepted by `genkit.Generate` (and `GenerateText` / `GenerateData`), by `genkit.DefinePrompt`, and by `Prompt.Execute` / `ExecuteStream`. There are four ways to reach it.

**Per call.** Pass the middleware's config struct to the generation you want it on. This is the default and it needs no registration: the value carries its own config, so Genkit calls its `New` method directly.

```go
resp, err := genkit.Generate(ctx, g,
    ai.WithPrompt("Summarize the release notes."),
    ai.WithUse(&middleware.Retry{MaxRetries: 2}),
)
```

The built-in middleware declare `Name` and `New` on value receivers, so a bare `middleware.Retry{...}` and a pointer `&middleware.Retry{...}` both satisfy `ai.Middleware`. These pages pass pointers.

**Inline.** For a one-off that needs no named type or Dev UI entry, adapt a closure with `ai.MiddlewareFunc`. See [Inline middleware](#inline-middleware) below.

**On a prompt definition.** Middleware passed to `genkit.DefinePrompt` applies to every execution of that prompt.

```go
p := genkit.DefinePrompt(g, "assistant",
    ai.WithPrompt("{{query}}"),
    ai.WithUse(&middleware.Retry{MaxRetries: 2}),
)

// Inherits the prompt's middleware.
resp, err := p.Execute(ctx, ai.WithInput(map[string]any{"query": "hello"}))

// Replaces it: only Fallback runs on this execution, Retry does not.
resp, err = p.Execute(ctx,
    ai.WithInput(map[string]any{"query": "hello"}),
    ai.WithUse(&middleware.Fallback{}),
)
```

Prompt-level and execute-level middleware do **not** merge. `ai.WithUse` at execute time replaces the whole chain the prompt was defined with.

**By name.** Middleware that is registered, either by a plugin or by `genkit.DefineMiddleware`, can be selected by name from a `.prompt` file's `use:` frontmatter. Each entry is a bare name or a `name` with a `config` map:

```yaml
---
model: googleai/gemini-flash-latest
use:
  - name: genkit-middleware/retry
    config:
      maxRetries: 2
  - genkit-middleware/skills
---
```

These entries resolve through the registry at execute time, so the plugin providing them has to be registered or the execution fails with `NOT_FOUND`. The `Middleware` plugin registers `genkit-middleware/retry`, `genkit-middleware/fallback`, `genkit-middleware/toolApproval`, `genkit-middleware/softToolErrors`, `genkit-middleware/skills`, and `genkit-middleware/filesystem`.

## Available middleware

The `plugins/middleware` package provides several useful middleware options out of the box. This list represents the middleware built and maintained by the Genkit team, but there may also be community-built middleware available.

### 1. Retry middleware (`Retry`)

Automatically retries failed model API calls on transient error codes (such as `RESOURCE_EXHAUSTED` and `UNAVAILABLE`) using exponential backoff with jitter. Only the model API call is retried; the surrounding tool loop is not replayed.

Genkit does not retry on its own. A bare `genkit.Generate` makes exactly one attempt per model call, and `Retry` is entirely opt-in.

:::caution
Your provider plugin may retry underneath the middleware, and the two counts multiply rather than add. With the AWS Bedrock plugin's default of 3 SDK retries, `&middleware.Retry{MaxRetries: 3}` permits up to 16 provider calls. Set the SDK's retry count to 0 when you use the middleware, or drop the middleware and rely on the SDK. See [`MaxRetries`](/docs/integrations/aws-bedrock) for Bedrock and [`option.WithMaxRetries`](/docs/integrations/anthropic) for Anthropic.
:::

```go
resp, err := genkit.Generate(ctx, g,
    ai.WithModelName("googleai/gemini-flash-latest"),
    ai.WithPrompt("Heavy reasoning task..."),
    ai.WithUse(&middleware.Retry{
        MaxRetries:     3,
        InitialDelayMs: 1000,
        BackoffFactor:  2,
    }),
)
```

**Configuration options:**

- `MaxRetries` (optional): The number of retries after the first attempt (default: 3). `MaxRetries: 3` allows up to four model calls in total.
- `Statuses` (optional): A list of `status.Name` values, from `github.com/firebase/genkit/go/core/status`, that should trigger a retry (default: `status.Unavailable`, `status.DeadlineExceeded`, `status.ResourceExhausted`, `status.Aborted`, `status.Internal`). The Developer UI offers every status name as a multi-select, and `status.Names()` returns that full list in code.
- `InitialDelayMs` (optional): The initial delay between retries in milliseconds (default: 1000).
- `MaxDelayMs` (optional): The upper bound on retry delay in milliseconds (default: 60000).
- `BackoffFactor` (optional): The factor by which the delay increases after each retry (default: 2).
- `NoJitter` (optional): If true, disables random jitter on the delay (default: false).

**What counts as retryable.** The decision turns on whether the error is classified, not on its Go type:

```go
func isRetryable(err error, statuses []status.Name) bool {
    if s, ok := status.Classified(err); ok {
        return slices.Contains(statuses, s)
    }
    return true
}
```

A classified error is retried only when its status is on the list. An **unclassified** error is always retried, whatever the list says, because a provider SDK error that carries no Genkit status is usually a transport failure worth another attempt. Two consequences are worth knowing:

- A cancelled context classifies as `CANCELLED`, which is not on the default list, so cancelling stops the retries. A `context.DeadlineExceeded` classifies as `DEADLINE_EXCEEDED`, which is on the list, so it is retried.
- Wrapping an error with `%v` instead of `%w` destroys its classification. That silently converts a non-retryable `INVALID_ARGUMENT` into an always-retried unclassified error.

**Deadlines and cancellation.** Genkit sets no default request timeout. The deadline on the context you hand `genkit.Generate` is the only bound, so give it one:

```go
func handler(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), 60*time.Second)
    defer cancel()

    resp, err := genkit.Generate(ctx, g,
        ai.WithPrompt("Summarize the release notes."),
        ai.WithUse(&middleware.Retry{MaxRetries: 3}),
    )
    if err != nil {
        http.Error(w, err.Error(), http.StatusInternalServerError)
        return
    }
    w.Write([]byte(resp.Text()))
}
```

That one deadline covers every retry attempt; it does not restart per attempt, and the backoff waits come out of the same budget. `&middleware.Retry{MaxRetries: 3, InitialDelayMs: 1000, BackoffFactor: 2}` spends 1s, then 2s, then 4s sleeping alone, before counting any time in the model. Size the timeout for the whole cascade, not for one call.

Cancelling the context stops the retries: a cancelled context classifies as `CANCELLED`, which is not on the retry list. Because `r.Context()` is cancelled when the HTTP client disconnects, an abandoned request stops burning attempts on its own.

### 2. Fallback middleware (`Fallback`)

Automatically switches to a different model if the primary model fails on a fallback-eligible status. Useful for falling back to a smaller or faster model when a large model exceeds quota limits.

```go
resp, err := genkit.Generate(ctx, g,
    ai.WithModelName("googleai/gemini-pro-latest"),
    ai.WithPrompt("Try the pro model first..."),
    ai.WithUse(&middleware.Fallback{
        Models: []ai.ModelRef{
            googlegenai.ModelRef("googleai/gemini-flash-latest", nil),
        },
        Statuses: []status.Name{status.ResourceExhausted},
    }),
)
```

**Configuration options:**

- `Models` (required): An ordered list of `ai.ModelRef` values to try after the primary fails. Each ref's `Config` is used verbatim for that model; the original request's config is **not** inherited. Use `googlegenai.ModelRef` (or the equivalent helper for your provider) to attach configuration. A named model that is not registered fails with `ai.ErrModelNotFound`.
- `Statuses` (optional): A list of `status.Name` values that should trigger a fallback (default: `status.Unavailable`, `status.DeadlineExceeded`, `status.ResourceExhausted`, `status.Aborted`, `status.Internal`, `status.NotFound`, `status.Unimplemented`). The two entries `Retry` does not share are `NotFound` and `Unimplemented`, so a model the provider does not serve fails over instead of failing.

**What counts as fallback-eligible.** The predicate is `Retry`'s with one line changed:

```go
func isFallbackRetryable(err error, statuses []status.Name) bool {
    if s, ok := status.Classified(err); ok {
        return slices.Contains(statuses, s)
    }
    return false
}
```

An unclassified error never triggers a fallback; it propagates immediately. This is the deliberate opposite of `Retry`, and the reason is cost: moving a request to a different billed model is a bigger action than reissuing the same one, so it demands an explicit classification. A plugin that classifies its provider's errors, for example with `status.Base(status.FromHTTPCode(code))`, is what makes fallback work at all.

**Models that fail for good are skipped.** `Fallback` acts per model call, so in a tool loop each turn starts at the primary again. A model that falls back with a status that does not clear up between calls (`NotFound`, `PermissionDenied`, `Unauthenticated`, `InvalidArgument`, or `Unimplemented`, when `Statuses` lists it) is skipped for the rest of that generate call, and each later turn starts at the next model. Transient statuses such as `Unavailable` and `ResourceExhausted` try the primary again on the next turn, and the next generate call tries every model again.

The [retry-fallback sample](https://github.com/genkit-ai/genkit/tree/main/go/samples/basic-middleware/retry-fallback) composes the two, pointing the primary at a model id that does not exist so the cascade fires on every run.

### 3. Tool approval middleware (`ToolApproval`)

Restricts tool execution to an allow list. A call to any other tool is held: the generation stops with an interrupt, and you resume it with a decision for each held call. With a [judge model](#let-a-judge-model-decide) set, a model decides those calls instead and holds only the ones it is unsure about.

```go
type WriteFileInput struct {
    Path    string `json:"path"`
    Content string `json:"content"`
}

writeFile := genkit.DefineTool(g, "write_file", "Write a text file.",
    func(ctx *ai.ToolContext, in WriteFileInput) (string, error) {
        if err := os.WriteFile(in.Path, []byte(in.Content), 0o600); err != nil {
            return "", err
        }
        return "wrote " + in.Path, nil
    })

approval := &middleware.ToolApproval{
    AllowedTools: []string{}, // An empty list holds every tool call.
}

// 1. Initial attempt: any tool not in AllowedTools holds the call.
resp, err := genkit.Generate(ctx, g,
    ai.WithPrompt("Write hello.txt with a short greeting."),
    ai.WithTools(writeFile),
    ai.WithUse(approval),
)
if err != nil {
    log.Fatal(err)
}

if resp.FinishReason == ai.FinishReasonInterrupted {
    // 2. One turn can hold several calls. Decide each one.
    var answers []*ai.Part
    for _, part := range resp.Interrupts() {
        call, ok := middleware.ToolApprovalInterrupted(part)
        if !ok {
            continue // A tool's own interrupt: claim it with that tool.
        }
        // Show the tool name and call.Input to the user.
        if confirm(part.ToolRequest.Name, call.Input) {
            answers = append(answers, call.Restart(middleware.ToolCallDecision{Approved: true}))
        } else {
            answers = append(answers, call.Restart(middleware.ToolCallDecision{Reason: "the user declined"}))
        }
    }

    // 3. Resume, with the same tools and middleware as the first call.
    resp, err = genkit.Generate(ctx, g,
        ai.WithMessages(resp.History()...),
        ai.WithTools(writeFile),
        ai.WithResume(answers...),
        ai.WithUse(approval),
    )
    if err != nil {
        log.Fatal(err)
    }
}
```

`confirm` stands for your own approval UI. `middleware.ToolApprovalInterrupted` claims a call that `ToolApproval` held and returns it typed: `call.Input` is the tool's input, and `call.Restart` takes a `middleware.ToolCallDecision`. Every restart of a hold decides it:

- `Approved: true` runs the tool.
- Any other restart refuses the call, a bare one included, so no resume flow gets past approval by leaving the field out. The model receives the refusal as the tool's error, with `Reason` when you set one, and the generation continues.

Answer a hold with `Restart`, not `Respond`. A response stands in for the tool's output, must match the tool's output schema, and does not refuse the call. The hold's data is `{"message": "..."}`; read it with `ai.InterruptAs[map[string]any](call.Part)`.

The hold is the middleware's own interrupt, so a tool's claim (`myTool.Interrupted(part)`) declines it, and `ToolApprovalInterrupted` declines a tool's own interrupt. Once approved, the tool runs as a fresh call and can interrupt with a question of its own, which you answer through the tool as described in [Pause generation using interrupts](/docs/interrupts/). The restart that answers that question passes the gate without a second approval, unless it replaces the call's input, which the gate then holds again.

A blocked call is still visible in traces: when a `WrapTool` hook resolves a call without running the tool, Genkit emits the tool span the tool itself would have produced.

**Configuration options:**

- `AllowedTools` (defaults to holding every tool): The tool names pre-approved to run without a hold. The gate is a membership test, so a nil slice and an empty slice behave identically. There is no wildcard. Tools that other middleware add are covered too, so list them by name: `Skills` exports its tool names as constants for this.
- `Judge` (optional): The model that decides each call `AllowedTools` does not cover. The zero value holds those calls.
- `JudgePolicy` (optional): Extra rules for the judge, in natural language, added to its instructions.

Every `ToolApproval` in one chain claims the same holds, since a claim matches the middleware's name.

#### Let a judge model decide

A judge is a model that decides the calls the allow list does not cover, in place of an unconditional hold. This is the auto-approval mode that coding agents offer: routine calls run, and only the questionable ones reach the user.

```go
approval := &middleware.ToolApproval{
    AllowedTools: []string{"list_files", "read_file"},
    Judge:        googlegenai.ModelRef("googleai/gemini-flash-lite-latest", nil),
    JudgePolicy:  "Never allow deleting anything outside the build directory.",
}
```

The judge answers each call with one of three verdicts:

- `allow` runs the tool.
- `deny` answers the call with an error the model sees, as a refusal does, and the generation continues.
- `ask` holds the call for you, as a call without a judge is held.

The judge fails closed: an error, or an answer that is not a verdict, holds the call. The hold's data then carries a `judge` key, `"ask"` or `"failed"`, so a resume UI can tell a judge that wants confirmation from one that could not decide. A hold you answer is your decision, and the judge does not revisit it.

The judge sees the text the user wrote and the pending call (the tool's name, description, and input) as one JSON document. Model text, tool results, retrieved documents, and the file contents the `Filesystem` middleware adds never reach it, since injected instructions usually arrive through those.

Each judged call costs one model call, so pick a model that is small and fast. The judge answers through the enum output format, so any model that can pick from a list of values works, including [decision models](/docs/integrations/system-one/) such as TypeSafe's jev, which answer in a fraction of the time a general model takes.

### 4. Skills middleware (`Skills`)

Makes a library of skills available to the model, following the [Agent Skills specification](https://agentskills.io), so a skill directory written for any compliant agent works unchanged. A skill is a directory with a `SKILL.md` file: YAML frontmatter with a `name` and a `description`, then the instructions. The middleware discloses skills in three tiers:

- **Catalog.** The system prompt lists each skill's name and description, and names the tool that loads one.
- **Instructions.** The `use_skill` tool, taking a single `skillName` string, returns the skill's full `SKILL.md`. A skill already loaded in the conversation is not sent twice.
- **Resources.** With `AllowResourceAccess` set, each load lists the files the skill bundles, and the `read_skill_file` tool reads one of them.

Keeping the heavy instructions behind a tool is the point: only the name and description of each skill are on the hot path.

```go
resp, err := genkit.Generate(ctx, g,
    ai.WithPrompt("How do I run tests in this repo?"),
    ai.WithUse(&middleware.Skills{SkillPaths: []string{"./skills"}}),
)
```

**Configuration options:**

- `SkillPaths` (optional): A list of directories to scan for skills. Each direct subdirectory containing a `SKILL.md` file is exposed as a skill (default: `[".agents/skills", "skills"]`, resolved against the process working directory). When two paths hold a skill of the same name, the later path wins, and the log says so.
- `Preload` (optional): Skills whose instructions are injected before the first model turn, for when the application rather than the model decides that a skill applies. Preloaded skills leave the catalog. A name that matches no skill is logged and ignored.
- `AllowResourceAccess` (optional): If true, registers `read_skill_file` and lists each skill's bundled files when it loads (default: false). Reads are confined to that one skill's directory, so `..`, absolute paths, and symbolic links that leave it are refused, and each read is capped at 256 KiB.
- `ToolNamePrefix` (optional): A prefix prepended to each tool name. Use distinct prefixes when attaching more than one `Skills` middleware to one call, since duplicate tool names fail the request.
- `SkillFS` (optional): A file system to read `SkillPaths` from, in place of the disk. It is not part of the JSON configuration, so a call that the Dev UI dispatches by name reads from disk.

Use `SkillFS` to ship skills inside the binary:

```go
//go:embed skills
var skillsFS embed.FS

resp, err := genkit.Generate(ctx, g,
    ai.WithPrompt("How do I run tests in this repo?"),
    ai.WithUse(&middleware.Skills{SkillFS: skillsFS}),
)
```

The default paths apply inside `SkillFS`. A `go:embed` pattern that names a directory leaves out the files in it whose names start with `.` or `_`, so name `.agents/skills` in the pattern itself, and add the `all:` prefix if a skill bundles such a file.

`ToolApproval.AllowedTools` matches tool names exactly, so name the skills tools with the exported constants `middleware.SkillToolName` (`use_skill`) and `middleware.SkillResourceToolName` (`read_skill_file`), after your `ToolNamePrefix` when you set one:

```go
resp, err := genkit.Generate(ctx, g,
    ai.WithPrompt("How do I run tests in this repo?"),
    ai.WithUse(
        &middleware.Skills{AllowResourceAccess: true},
        &middleware.ToolApproval{AllowedTools: []string{
            middleware.SkillToolName,
            middleware.SkillResourceToolName,
        }},
    ),
)
```

Details of the scan worth knowing:

- The **directory name** is the skill name the model uses. The `name` field in the frontmatter does not change it, so a directory named `python-helper` is `python-helper` no matter what the file says.
- Discovery is one level deep. Direct subdirectories are considered, nested ones are not, and names starting with `.` are skipped. A symbolic link to a skill directory is followed, but the `SKILL.md` itself must be a regular file named exactly `SKILL.md`, of at most 1 MiB.
- A path that cannot be read is skipped rather than fatal, with a record in the log. A mistyped `SkillPaths` entry therefore yields no skills and no error, and with no skills found, no tool is registered.
- A skill whose frontmatter is malformed still loads, with a record in the log, so a library written for another agent keeps working.

A failed skills tool call, such as one naming a skill that does not exist, answers the call with a message that lists the valid names, so the generation continues. Each part that carries a skill's instructions has the skill's name in its metadata under `middleware.SkillActivationMetadataKey`, which context-management middleware can use to find skill instructions in a transcript.

A discovered `SKILL.md` becomes instruction text that the model follows. Treat a skills tree the way you treat source code, and prefer absolute paths over the defaults in a server process.

Loading a skill costs a turn of the tool loop, which counts toward `ai.WithMaxTurns`. The [skills sample](https://github.com/genkit-ai/genkit/tree/main/go/samples/basic-middleware/skills) ships four deliberately loud personas so the effect of a load is visible in one run.

### 5. Filesystem middleware (`Filesystem`)

Grants the model access to a single root directory by injecting file manipulation tools. Two are always registered, `list_files` and `read_file`; `write_file` and `edit_file` join them only when `AllowWriteAccess` is true. Paths are relative to the root, and an absolute path such as `/notes.txt` is read as `notes.txt` inside it. Path safety is enforced by `os.Root`, which rejects any path that resolves outside the root, including via `..` or symbolic links.

```go
resp, err := genkit.Generate(ctx, g,
    ai.WithPrompt("Create a hello world program in the workspace"),
    ai.WithUse(&middleware.Filesystem{
        RootDir:          "./workspace",
        AllowWriteAccess: true,
    }),
)
```

**Configuration options:**

- `RootDir` (required): The root directory all filesystem operations are confined to. Its JSON key is `rootDirectory`, which is the name to use in `.prompt` frontmatter and the Dev UI. An empty value fails with `INVALID_ARGUMENT`.
- `AllowWriteAccess` (optional): If true, additionally registers `write_file` and `edit_file` (default: false).
- `ToolNamePrefix` (optional): A prefix prepended verbatim to each tool name, so `"repo_"` yields `repo_list_files` and the rest. Use distinct prefixes when attaching multiple `Filesystem` middlewares to one call so their tool names don't collide.

A failed file operation, such as a missing file or an edit that does not match, does not fail the generation. Its error answers the call under the same rules as [`SoftToolErrors`](#6-soft-tool-errors-middleware-softtoolerrors), so the model can correct its path or edit. Errors of other tools, errors that other hooks return, and cancellation still stop the generation.

`read_file` does not return the file in its tool result. It answers with a short summary and injects the contents as a user message on the next turn, which is why the middleware needs a `WrapGenerate` hook as well as tools. `edit_file` refuses to touch a file that was not read earlier in the same call, and `write_file` refuses to overwrite an existing one that was not read; both refuse again if the file changed on disk since that read. Creating a new file with `write_file` needs no prior read.

The [filesystem sample](https://github.com/genkit-ai/genkit/tree/main/go/samples/basic-middleware/filesystem) ships a small mock project and one flow per mode, read-only and write-enabled.

### 6. Soft tool errors middleware (`SoftToolErrors`)

A tool error fails the generation with `ai.ErrToolFailed` by default. `SoftToolErrors` returns tool errors to the model instead: the error answers the tool call, the model can correct its input and try again, and the loop continues. Use it for tools you do not own, such as MCP tools or tools that another middleware adds.

```go
resp, err := genkit.Generate(ctx, g,
    ai.WithPrompt("What is the weather in Paris?"),
    ai.WithTools(weatherTool),
    ai.WithUse(&middleware.SoftToolErrors{}),
)
```

The model receives `{"error": "<message>"}` as the tool's output, with `{"isError": true}` in the part's metadata. `Part.IsToolError` reports such a response, and model plugins whose API marks tool errors, such as Anthropic's `is_error`, read it.

How it decides:

- It covers the errors a tool returns, input validation errors included, and calls to tool names that do not exist.
- Interrupts, cancellation, and an error that a `WrapTool` hook returns in place of the tool's own still stop the generation. A hook that wraps the tool's error with `%w` keeps it covered.
- The conversion happens after the whole `WrapTool` chain, so every hook, a retry included, sees the error first, wherever `SoftToolErrors` sits in the chain.
- The policy belongs to one `Generate`. A `Generate` that a tool runs does not inherit it.

**Configuration options:**

- `Tools` (optional): Limits the middleware to these tool names. Empty covers every tool, and calls to tools that do not exist.

A tool you own can return one specific error to the model without this middleware: return `tool.Fail(ctx, err)` from `github.com/firebase/genkit/go/ai/tool`. Only the author knows which errors the model can fix, so mark those and let the rest stop the loop. See [Return an error to the model](/docs/tool-calling/#return-an-error-to-the-model).

### 7. Context compression middleware (`ContextCompression`)

:::caution[Preview]
This middleware is in the experimental `plugins/middleware/exp` package and can change in a minor release.
:::

Keeps a conversation inside a context budget through long chats and tool loops. When the context grows past a trigger, the middleware compresses what the model receives, cheapest strategy first, while the history you get back keeps every message.

```go
import (
    "github.com/firebase/genkit/go/plugins/middleware"
    middlewarex "github.com/firebase/genkit/go/plugins/middleware/exp"
)

resp, err := genkit.Generate(ctx, g,
    ai.WithModelName("googleai/gemini-flash-latest"),
    ai.WithPrompt("Research this topic thoroughly."),
    ai.WithTools(searchTool),
    ai.WithUse(
        &middlewarex.ContextCompression{
            MaxInputTokens:        80_000,
            DedupeToolResponses:   &middlewarex.CompressionDedupe{},
            TruncateToolResponses: &middlewarex.CompressionToolTruncation{MaxChars: 2000},
            Summarize: &middlewarex.CompressionSummarizer{
                Model: googlegenai.ModelRef("googleai/gemini-flash-lite-latest", nil),
            },
        },
        &middleware.Retry{}, // Inside compression, so a retry resends the compressed view.
    ),
)
```

Before each tool-loop iteration, compression runs when the context exceeds `MaxInputTokens` (the input tokens the model reported for the previous call, estimated from the messages before there is one) or the conversation holds more than `MaxMessages` messages. The strategies run in order:

1. `DedupeToolResponses` replaces older duplicate tool responses with a short notice.
2. `TruncateToolResponses` truncates older tool responses, leaving the newest tool messages intact.
3. `Summarize` has a model fold older messages into a summary, unless the first two strategies already saved `SkipSummarizationThreshold` of the context and brought it under budget.
4. Older messages are dropped when nothing was summarized and the conversation is still over its message budget. A notice tells the model that context was removed.

Set `MaxInputTokens` well above the size of a typical first turn. The prompt of a plain `Generate` call is an ordinary user message, so a compaction early in a tool loop, far over budget, can fold the request itself into the summary, and the model then works from the summary of its task.

`MaxToolResponseChars` caps every tool response on every iteration, whether or not a trigger fires. Leading system messages are always kept, and the kept messages never start with a tool response separated from its request. The scaffolding an agent's prompt renders on every turn, and the message that carries output-format instructions, are never summarized or dropped.

**The model gets a view, the history keeps the transcript.** `resp.History()` keeps every original message, and the compression is recorded in their metadata under the `"contextCompression"` key. That metadata is the whole state, so compression continues across `Generate` calls, agent sessions, and process restarts when you carry the history forward, and a history that the JavaScript middleware compressed resolves the same way. `middlewarex.ResolveCompressedHistory(msgs)` returns the messages a model receives for a history. Set `ReplaceHistory` to get the compressed messages back as the history instead. The final response carries the newest compression's stats in `resp.Custom`, under `"contextCompression"`.

**Order.** List `ContextCompression` after middleware that adds context (`Skills`, `Filesystem`, `Agents`, `Artifacts`), so it accounts for what they add, and before `Retry` and `Fallback`, so retried and fallback calls receive the compressed view.

**Configuration options:**

- `MaxInputTokens` (optional): Compress when the context exceeds this many tokens. Zero disables the token trigger.
- `MaxMessages` (optional): Compress when the conversation holds more than this many messages, and keep at most this many. Zero disables it. Without `Summarize`, a tight cap drops the turns that record a tool loop's progress, and the model may repeat calls it already made.
- `PreserveRecent` (optional): How many of the newest non-system messages are kept when older ones are dropped, and the default window for `Summarize` (default: 4). This window and the summarizer's both shrink when the context is far over budget: they are halved, to no fewer than 2, beyond 1.5 times `MaxInputTokens`, and are at most 2 beyond twice it.
- `MaxToolResponseChars` (optional): A hard cap on the characters of any one tool response, applied on every iteration (default: 400000). Negative disables it.
- `DedupeToolResponses` (optional): A `*middlewarex.CompressionDedupe`. `MatchBy` matches duplicates by tool name and input (`middlewarex.CompressionDedupeNameAndInput`, the default) or by tool name alone (`middlewarex.CompressionDedupeNameOnly`); `KeepRecent` is how many of the newest responses in each group stay intact (default: 1); `Notice` replaces the default notice.
- `TruncateToolResponses` (optional): A `*middlewarex.CompressionToolTruncation`. `MaxChars` (required) is the most characters an older tool response keeps; `PreserveRecent` is how many of the newest tool messages stay intact (default: 2, negative truncates every tool message).
- `Summarize` (optional): A `*middlewarex.CompressionSummarizer`. `Model` (required) writes the summaries, with its config used as is, so set the summary's output limit there; `PreserveRecent` is how many of the newest messages stay out of the summary (default: the top-level `PreserveRecent` when set, 6 otherwise); `Prompt` replaces the default prompt, with each `{conversation}` in it replaced by the messages to summarize.
- `SkipSummarizationThreshold` (optional): Skip `Summarize` when deduplication and truncation saved at least this fraction of the context, between 0 and 1, and brought it under `MaxInputTokens`. Zero always summarizes.
- `TruncationNotice` (optional): A custom notice for dropped messages. `NoTruncationNotice` drops them without one.
- `ReplaceHistory` (optional): If true, the returned history is the compressed messages instead of the originals (default: false).

A nil strategy is off. `New` fails with `INVALID_ARGUMENT` for a negative count, a missing `MaxChars` or summarizer model, or a threshold outside 0 to 1, and with `ai.ErrModelNotFound` for a summarizer model that no plugin resolves.

The [context-compression sample](https://github.com/genkit-ai/genkit/tree/main/go/samples/basic-middleware/context-compression) runs a research loop with a small budget, so compression starts partway through, and reports what it compressed next to the answer.

### 8. Budget middleware (`Budget`)

:::caution[Preview]
This middleware is in the experimental `plugins/middleware/exp` package and can change in a minor release.
:::

Caps what a generate run, or an agent session, may spend. `Limit` is an `ai.GenerationUsage`, and each non-zero field is a cap, with `Custom` capped key by key, so tokens, images, and a cost that the provider reports are all covered.

```go
resp, err := genkit.Generate(ctx, g,
    ai.WithPrompt("Research the topic and summarize it."),
    ai.WithTools(searchTool),
    ai.WithUse(&middlewarex.Budget{Limit: ai.GenerationUsage{
        TotalTokens: 50_000,
    }}),
)
if errors.Is(err, ai.ErrBudgetExceeded) {
    // The partial response keeps the turns that ran.
    log.Printf("out of budget after %d tokens", resp.TotalUsage.TotalTokens)
}
```

Usage counts as models report it. `OutputTokens` leaves out `ThoughtsTokens`, so cap both, or `TotalTokens`, to cap what a model generates. A model that reports no usage spends nothing.

**When it stops.** The limit is checked before each model call of the tool loop, outside every `WrapModel` hook, so `Retry` and `Fallback` never see the stop, in any order. A turn that is already running finishes, so a run can go over its limit by one turn, and with `Retry` in the chain, one turn can be several billed calls. The run stops with `ai.ErrBudgetExceeded`. Like `ai.ErrMaxTurnsExceeded`, it is a limit the caller set: the partial response reports `ai.FinishReasonAborted`, and an agent turn reports aborted, not failed.

**What counts.** With the default run scope, every model call made under the `Generate` counts: the calls `resp.TotalUsage` sums (the tool loop, hooks, nested generates), plus those of any subagent the run starts, so delegation cannot spend around the cap. With `Scope: middlewarex.BudgetScopeSession`, the limit covers the agent session's recorded usage across all its turns, plus what the current run spends. That needs a server-managed agent with a [session store](/docs/agents/session-stores/), and `New` fails otherwise. A budget stops only the run it wraps: a background delegation the run started keeps running, and spending, after the run stops.

**Pausing instead of stopping.** With `Interrupt` set, a run-scoped budget holds the tool calls that would lead to the next turn, and you decide whether the run continues:

```go
budget := &middlewarex.Budget{
    Limit:     ai.GenerationUsage{TotalTokens: 50_000},
    Interrupt: true,
}

resp, err := genkit.Generate(ctx, g,
    ai.WithPrompt("Research the topic and summarize it."),
    ai.WithTools(searchTool),
    ai.WithUse(budget),
)
if err != nil {
    log.Fatal(err)
}

if resp.FinishReason == ai.FinishReasonInterrupted {
    var answers []*ai.Part
    for _, part := range resp.Interrupts() {
        if call, ok := middlewarex.BudgetInterrupted(part); ok {
            hold, _ := ai.InterruptAs[middlewarex.BudgetExceeded](call.Part)
            log.Printf("%s, approving more", hold.Message)
            answers = append(answers, call.Restart(middlewarex.BudgetDecision{Approved: true}))
        }
    }
    resp, err = genkit.Generate(ctx, g,
        ai.WithMessages(resp.History()...),
        ai.WithTools(searchTool),
        ai.WithResume(answers...),
        ai.WithUse(budget),
    )
}
```

`middlewarex.BudgetExceeded` says which limit the run reached: `Message`, plus `Spent` and `Limit` keyed by each capped field's JSON name, such as `"totalTokens"` or `"custom.cost"`. A `middlewarex.BudgetDecision` with `Approved: true` continues the run with the full limit again. Any other restart, a bare one included, stops the run with `ai.ErrBudgetExceeded` and your `Reason` before the held calls run, and so does a `Respond`. The holds of one run share one decision, so one refusal stops it.

The pause happens only when the run is over its limit by the time its tool calls start. A run that goes over while its tools run (a nested generate, a subagent) has nothing left to hold, and the check before the next model call stops it. A session-scoped budget cannot pause, since the next turn would start over its limit with no tool call to pause on, so `New` rejects that combination.

A run counts across its resumes. The run's final message records what it spent, and a resume of that conversation continues from there, so answering another middleware's hold, such as a `ToolApproval` hold, does not renew the limit; only approving the budget's own hold does. A history that comes back without that record, which a client-managed history can do, starts the count over.

**Configuration options:**

- `Limit` (required): The usage the run or session may spend. Each non-zero field is a cap, and at least one must be set.
- `Scope` (optional): `middlewarex.BudgetScopeRun` (the default) or `middlewarex.BudgetScopeSession`.
- `Interrupt` (optional): If true, a run-scoped budget pauses for approval instead of stopping (default: false).

Budgets in one chain count the same calls and claim the same holds, so stacking them enforces all their limits together. The [budget sample](https://github.com/genkit-ai/genkit/tree/main/go/samples/basic-middleware/budget) sends the model along a chain of clues that a small budget cannot reach the end of, once stopping and once pausing.

## Building your own custom middleware

A middleware in Go is any value that satisfies the `ai.Middleware` interface:

```go
type Middleware interface {
    Name() string                               // stable, registered identifier
    New(ctx context.Context) (*ai.Hooks, error) // builds a per-call hook bundle
}
```

`New` is invoked once per `genkit.Generate()` call. The returned `*ai.Hooks` bundle is reused across every iteration of the tool loop within that call:

```go
type Hooks struct {
    // Tools are extra tools to register for this Generate call alongside any user-supplied tools.
    Tools []ai.Tool

    // WrapGenerate wraps each iteration of the tool loop.
    WrapGenerate func(ctx context.Context, params *ai.GenerateParams, next ai.GenerateNext) (*ai.ModelResponse, error)

    // WrapModel wraps each model API call of this Generate call.
    WrapModel func(ctx context.Context, params *ai.ModelParams, next ai.ModelNext) (*ai.ModelResponse, error)

    // WrapTool wraps each tool execution. May run concurrently for parallel tool calls.
    WrapTool func(ctx context.Context, params *ai.ToolParams, next ai.ToolNext) (*ai.MultipartToolResponse, error)
}
```

Implement only the hooks your middleware needs. A nil hook field is treated as a pass-through. An error from `New` fails the generate call with the status it carries; an unclassified one reports `INVALID_ARGUMENT`, since a configuration the middleware rejects is the caller's mistake.

The middleware in this section draw on these imports:

```go
import (
    "context"
    "crypto/sha256"
    "encoding/hex"
    "encoding/json"
    "errors"
    "slices"
    "strings"
    "sync"
    "sync/atomic"
    "time"

    "github.com/firebase/genkit/go/ai"
    aix "github.com/firebase/genkit/go/ai/exp"
    "github.com/firebase/genkit/go/ai/tool"
    "github.com/firebase/genkit/go/core/logger"
    "github.com/firebase/genkit/go/core/status"
    "github.com/firebase/genkit/go/core/tracing"
    "github.com/firebase/genkit/go/genkit"
)
```

### When each hook fires

A `Generate` call runs a tool loop: the model produces output, any tool calls execute, results feed back into a new model call, and so on until the model stops. The hooks attach at three different layers of this loop:

| Hook           | Fires                                                                                            | Use for                                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| `WrapGenerate` | Once per tool-loop iteration. N tool turns means N+1 invocations.                                | Logic that needs to see the whole conversation: rewrites, system-prompt injection, message accumulation. |
| `WrapModel`    | Once per model API call, inside an iteration.                                                    | Logic about the model call itself: retry, fallback, caching.                                             |
| `WrapTool`     | Once per tool execution. May run **concurrently** for parallel tool calls in the same iteration. | Logic about a single tool execution: approval, sandboxing, logging.                                      |

`WrapGenerate` and `WrapModel` are not called concurrently within a single `Generate` call. `WrapTool` may be, since multiple tools can execute in parallel.

### What each hook receives

`ai.GenerateParams`, for `WrapGenerate`:

| Field          | Type                     | What it is                                                                                                                           |
| -------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| `Request`      | `*ai.ModelRequest`       | The model request for this turn, with the messages accumulated so far. Replace it or edit it to change what the model receives.       |
| `Options`      | `*ai.GenerateActionOptions` | A per-turn copy of the options `Generate` was called with, carrying what `Request` does not: `Model`, `MaxTurns`, resume directives. |
| `Iteration`    | `int`                    | The tool-loop iteration, 0-indexed.                                                                                                   |
| `MessageIndex` | `int`                    | The index of the next message in the streamed response sequence.                                                                      |
| `Callback`     | `ai.ModelStreamCallback` | The streaming callback, or nil when not streaming.                                                                                    |

`ai.ModelParams`, for `WrapModel`:

| Field      | Type                     | What it is                              |
| ---------- | ------------------------ | --------------------------------------- |
| `Request`  | `*ai.ModelRequest`       | The model request about to be sent.     |
| `Callback` | `ai.ModelStreamCallback` | The streaming callback, or nil.         |

`ai.ToolParams`, for `WrapTool`:

| Field     | Type              | What it is                                                                                                          |
| --------- | ----------------- | ------------------------------------------------------------------------------------------------------------------- |
| `Request` | `*ai.ToolRequest` | `Name` the tool name, `Input` the decoded arguments as `any`, `Ref` the model's call id, `Partial` for stream chunks. |
| `Tool`    | `ai.Tool`         | The resolved tool: `Tool.Name()`, `Tool.Definition()`.                                                               |

Both `Request` fields above are the same `*ai.ModelRequest`:

| Field        | Type                    |
| ------------ | ----------------------- |
| `Messages`   | `[]*ai.Message`         |
| `Config`     | `any`                   |
| `Tools`      | `[]*ai.ToolDefinition`  |
| `ToolChoice` | `ai.ToolChoice`         |
| `Output`     | `*ai.ModelOutputConfig` |
| `Docs`       | `[]*ai.Document`        |

:::note
`ai.ModelRequest` carries no model name. In `WrapGenerate`, read `params.Options.Model`. In `WrapModel`, the name is not on `params` at all: if needed, capture it in `WrapGenerate` and close over it.
:::

**Mutating params.** A hook may edit `params` in place, or build a different value and hand that to `next`; the engine reads whatever it is given. These rules follow from how the loop owns these values:

- `GenerateParams.Request` and `ModelParams.Request` are fresh per turn, so an in-place edit stays with that turn. The exception is a `*ai.Message` shared with the next turn: copy the message with `Clone()` before editing its text.
- `GenerateParams.Options` is a shallow per-turn copy. Writes to it reach nothing, so treat it as read-only.
- For redaction that must not reach the stored history, prefer `WrapModel`, and shallow-copy the `ModelRequest` plus only the messages and parts you change.
- Models record the request they ran on in the response's `Request`, and `ModelResponse.History()` reads the conversation from it. A `WrapModel` hook that sends the model different messages than it received must put the original messages back on the response's `Request`, or the caller's history becomes the messages the model saw.

Middleware that emits its own chunks through `Callback` must set `ModelResponseChunk.Role` and `Index` explicitly, and advance `GenerateParams.MessageIndex` so downstream middleware and the model see the shifted value.

**Short-circuiting.** A hook can return without calling `next`. `WrapTool` is the useful case: the tool never runs, but the model still receives an answer it can react to on the next turn. To refuse a call, return `tool.Fail` from `github.com/firebase/genkit/go/ai/tool`, and the model receives the error as the tool's response, the same shape `SoftToolErrors` produces:

```go
type ToolRefusal struct {
    Denied []string `json:"denied,omitempty"`
}

func (ToolRefusal) Name() string { return "mine/toolRefusal" }

func (tr ToolRefusal) New(context.Context) (*ai.Hooks, error) {
    return &ai.Hooks{
        WrapTool: func(ctx context.Context, p *ai.ToolParams, next ai.ToolNext) (*ai.MultipartToolResponse, error) {
            if slices.Contains(tr.Denied, p.Request.Name) {
                return nil, tool.Fail(ctx, errors.New("denied by policy: "+p.Request.Name))
            }
            return next(ctx, p)
        },
    }, nil
}
```

Any other error from a `WrapTool` hook stops the generation. To answer with a result instead, such as a cached one, return an `*ai.MultipartToolResponse` without calling `next`. A hook that skips `next` still produces the tool span, so the refusal is visible in traces.

### Logging from a hook

Log through the `core/logger` helpers in `github.com/firebase/genkit/go/core/logger` rather than through `log` or `fmt`. They take the context as their first argument, and that context is what carries the active span, so each record lands on the trace it belongs to and shows up in the Dev UI beside the span that produced it:

```go
func Debug(ctx context.Context, msg string, args ...any)
func Info(ctx context.Context, msg string, args ...any)
func Warn(ctx context.Context, msg string, args ...any)
func Error(ctx context.Context, msg string, args ...any)
```

Before writing a middleware whose only job is to log, check whether you need it: Genkit already brackets every generate, model, and tool hook with debug records carrying the middleware name, the hook, its duration, whether it short-circuited, and any error. Middleware is the one layer with no span of its own, so those records exist to fill that gap. Hand-rolled timing middleware usually duplicates them.

### A simple example

Here is a custom middleware that reports how long each model call takes, along with a label from its config:

```go
type Timing struct {
    Label string `json:"label,omitempty" jsonschema_description:"Label attached to each timing record."`
}

func (Timing) Name() string { return "mine/timing" }

func (t Timing) New(ctx context.Context) (*ai.Hooks, error) {
    return &ai.Hooks{
        WrapModel: func(ctx context.Context, p *ai.ModelParams, next ai.ModelNext) (*ai.ModelResponse, error) {
            start := time.Now()
            resp, err := next(ctx, p)
            logger.Info(ctx, "model call finished",
                "label", t.Label,
                "duration", time.Since(start).Round(time.Millisecond),
                "error", err)
            return resp, err
        },
    }, nil
}
```

To use it:

```go
resp, err := genkit.Generate(ctx, g,
    ai.WithPrompt("Hello"),
    ai.WithUse(Timing{Label: "demo"}),
)
```

Note the receivers. `Timing` declares `Name` and `New` on value receivers, so a bare `Timing{...}` satisfies `ai.Middleware`, and so does `&Timing{...}`. Prefer value receivers: a registered middleware is copied before each JSON-dispatched call decodes its config, so a pointer receiver buys nothing.

The `jsonschema_description` tag is how a config field gets documented. Genkit infers the config schema from the struct without reading Go doc comments, and the Developer UI renders the tag's text as the field's tooltip. Keep constraints such as `enum=` in the separate `jsonschema` tag, whose comma-separated keyword list would otherwise cut a description off at its first comma.

### Sharing state across hooks

State that should be shared across the hooks of a single `Generate` call lives in **closures captured by `New`**. Each call gets a fresh `Hooks` bundle, so nothing leaks between calls:

```go
type Counter struct{}

func (Counter) Name() string { return "mine/counter" }

func (Counter) New(ctx context.Context) (*ai.Hooks, error) {
    var modelCalls int
    return &ai.Hooks{
        WrapModel: func(ctx context.Context, p *ai.ModelParams, next ai.ModelNext) (*ai.ModelResponse, error) {
            modelCalls++
            return next(ctx, p)
        },
        WrapGenerate: func(ctx context.Context, p *ai.GenerateParams, next ai.GenerateNext) (*ai.ModelResponse, error) {
            // The same `modelCalls` is visible here: both closures capture it from `New`.
            resp, err := next(ctx, p)
            logger.Debug(ctx, "iteration finished", "iteration", p.Iteration, "modelCalls", modelCalls)
            return resp, err
        },
    }, nil
}
```

`WrapTool` may run concurrently for parallel tool calls in the same iteration, so any state it touches must be guarded with sync primitives:

```go
func (Counter) New(ctx context.Context) (*ai.Hooks, error) {
    var (
        mu        sync.Mutex
        toolCalls int
    )
    return &ai.Hooks{
        WrapTool: func(ctx context.Context, p *ai.ToolParams, next ai.ToolNext) (*ai.MultipartToolResponse, error) {
            mu.Lock()
            toolCalls++
            mu.Unlock()
            return next(ctx, p)
        },
    }, nil
}
```

The built-in `Filesystem` middleware uses this pattern: `New` allocates a per-call file-state cache and a path-lock map, then the read, write, and edit tool implementations close over both.

### Holding a tool call for the caller

A `WrapTool` hook can also pause a call without running it, the way `ToolApproval` does, and read the caller's answer when the generation resumes. Three verbs from `github.com/firebase/genkit/go/ai/tool` do the work:

- `tool.Interrupt(ctx, data)` holds the call. Return it from the hook. `data` must serialize to a JSON object, a struct or a map.
- `tool.ResumeData[T](ctx)` reads the answer in the hook that raised the hold, when the restart answers it.
- `tool.Released(ctx)` reports that this hook let the call through before the call paused at a later stage, such as the tool's own interrupt. Pass such a call on rather than holding it again.

```go
// SpendApproval holds calls to the listed tools until the caller decides them.
type SpendApproval struct {
    Tools []string `json:"tools,omitempty" jsonschema_description:"Tools whose calls need approval."`
}

// SpendHold is the data a SpendApproval hold carries.
type SpendHold struct {
    Tool string `json:"tool"`
}

// SpendDecision is the caller's answer to a SpendApproval hold.
type SpendDecision struct {
    Approved bool   `json:"approved"`
    Reason   string `json:"reason,omitempty"`
}

func (SpendApproval) Name() string { return "mine/spendApproval" }

func (s SpendApproval) New(context.Context) (*ai.Hooks, error) {
    return &ai.Hooks{
        WrapTool: func(ctx context.Context, p *ai.ToolParams, next ai.ToolNext) (*ai.MultipartToolResponse, error) {
            if !slices.Contains(s.Tools, p.Tool.Name()) {
                return next(ctx, p)
            }
            // This hook let the call through before it paused for another reason.
            if tool.Released(ctx) {
                return next(ctx, p)
            }
            // The restart answers this hook's hold.
            if d, ok := tool.ResumeData[SpendDecision](ctx); ok {
                if d.Approved {
                    return next(ctx, p)
                }
                return nil, tool.Fail(ctx, errors.New("the user declined this call: "+d.Reason))
            }
            return nil, tool.Interrupt(ctx, SpendHold{Tool: p.Tool.Name()})
        },
    }, nil
}
```

The context names the stage that raises the hold, and the restart that answers it reaches that stage alone. A hook's stage is its middleware name, with a `#n` suffix when the name repeats in the chain. Once the hook lets the call through, the tool runs as a fresh call and can interrupt on its own; the restart that answers the tool finds `tool.Released` true in this hook. `tool.Released` is false when that restart replaces the call's input, so a revised call gets a new decision.

Give callers a typed claim, so they answer your holds the way they answer a tool's interrupts. Wrap `ai.MiddlewareInterrupted[Res](name, part)` in a function that fixes the middleware name and the answer type:

```go
// SpendApprovalInterrupted reports whether part is a call SpendApproval held
// and, when it is, returns the call, to be answered with a SpendDecision.
func SpendApprovalInterrupted(part *ai.Part) (*ai.InterruptedCall[any, any, SpendDecision], bool) {
    return ai.MiddlewareInterrupted[SpendDecision](SpendApproval{}.Name(), part)
}
```

The claim matches the hold's stage, so a tool's own interrupt and another middleware's hold report false. The call's input and output types are `any`, since a hook holds any tool, and the answer type must serialize to a JSON object. A caller then decides each hold with `call.Restart`:

```go
var answers []*ai.Part
for _, part := range resp.Interrupts() {
    if call, ok := SpendApprovalInterrupted(part); ok {
        hold, _ := ai.InterruptAs[SpendHold](call.Part)
        answers = append(answers, call.Restart(SpendDecision{Approved: confirm(hold.Tool, call.Input)}))
    }
}
```

Carry a refusal as a field of the answer type and answer it with `tool.Fail`, as above: `call.Respond` stands in for the tool's output, must match its output schema, and never reaches the hook. The caller's side of resuming, with `ai.WithResume`, is described in [Pause generation using interrupts](/docs/interrupts/).

### Counting usage across nested calls

A caller reads what a run spent from `resp.TotalUsage`, the sum of every model call the run made: the tool loop's calls, and the calls its tools and hooks make, such as a fallback model or a nested generate. `resp.Usage` is the last call alone.

A `WrapModel` hook sees only the model calls of the `Generate` it is attached to, so a middleware that meters or caps usage there misses a `Generate` that a tool runs, a judge, or a subagent. Add an `aix.Observer` to the context with `tracing.WithInstrumentation` instead: it sees every model call made under that context, whoever makes it. Add it in the first iteration of `WrapGenerate`, whose context every later iteration runs under:

:::caution[Preview]
`aix.Observer` is in the experimental `ai/exp` package and can change in a minor release.
:::

```go
// TokenCap stops a run once its model calls, nested ones included, spend
// MaxTokens.
type TokenCap struct {
    MaxTokens int `json:"maxTokens" jsonschema_description:"Tokens the run may spend."`
}

func (TokenCap) Name() string { return "mine/tokenCap" }

func (c TokenCap) New(context.Context) (*ai.Hooks, error) {
    var spent atomic.Int64
    return &ai.Hooks{
        WrapGenerate: func(ctx context.Context, p *ai.GenerateParams, next ai.GenerateNext) (*ai.ModelResponse, error) {
            if p.Iteration == 0 {
                ctx = tracing.WithInstrumentation(ctx, aix.Observer{
                    ModelDone: func(_ context.Context, call *aix.ModelCall) {
                        if u := call.Response.Usage; u != nil {
                            spent.Add(int64(u.TotalTokens))
                        }
                    },
                })
            }
            if n := spent.Load(); n >= int64(c.MaxTokens) {
                return nil, status.Errorf(ai.ErrBudgetExceeded, "spent %d of %d tokens", n, c.MaxTokens)
            }
            return next(ctx, p)
        },
    }, nil
}
```

`ModelDone` runs on the goroutine that made the call, and calls can run concurrently, so guard the state it touches. `call.Response` is never nil, and failed calls are reported too. A response that a `WrapModel` hook supplies without calling the model, such as a cache hit, is not a model call and is not reported, and neither is a background model. Returning `ai.ErrBudgetExceeded` makes the partial response report `ai.FinishReasonAborted`, as the built-in [`Budget`](#8-budget-middleware-budget) does; use `Budget` itself unless you need different rules.

An application can add the same observer around a flow, to meter usage per tenant. The [metering sample](https://github.com/genkit-ai/genkit/tree/main/go/samples/basic-middleware/metering) bills a tool's nested model call at that model's own rate.

### Illustrative example: Guardrails middleware

The following example demonstrates how to build an illustrative custom middleware that performs pre- and post-generation policy checks. Using `WrapModel` and `WrapGenerate`, the middleware can evaluate inputs before an expensive model invocation runs, and inspect outputs before returning them to the caller:

```go
// Guardrail screens the request before the model runs, and checks the
// response before the caller sees it. Both hooks use a classifier model.
type Guardrail struct {
    Classifier string `json:"classifier,omitempty"`
}

func (Guardrail) Name() string { return "mine/guardrail" }

func (gr Guardrail) classify(ctx context.Context, instruction, text string) (string, error) {
    // Every generation carries its Genkit instance on the context.
    verdict, err := genkit.GenerateText(ctx, genkit.FromContext(ctx),
        ai.WithModelName(gr.Classifier),
        ai.WithSystem("%s Answer with one word: BLOCK if it does, ALLOW otherwise.", instruction),
        ai.WithPrompt("%s", text),
    )
    if err != nil {
        return "", err
    }
    return strings.TrimSpace(verdict), nil
}

func (gr Guardrail) New(context.Context) (*ai.Hooks, error) {
    return &ai.Hooks{
        // Input guardrail: screen before running the primary model.
        WrapModel: func(ctx context.Context, p *ai.ModelParams, next ai.ModelNext) (*ai.ModelResponse, error) {
            var sb strings.Builder
            for _, m := range p.Request.Messages {
                if m.Role == ai.RoleUser {
                    sb.WriteString(m.Text())
                    sb.WriteString("\n")
                }
            }
            verdict, err := gr.classify(ctx, "Does this request contain abuse?", sb.String())
            if err != nil {
                return nil, err
            }
            if verdict != "ALLOW" {
                // Returning without calling next: the primary model never runs.
                return nil, status.Errorf(status.ErrFailedPrecondition,
                    "input guardrail tripped: %s", verdict)
            }
            return next(ctx, p)
        },

        // Output guardrail: check the response before returning to the caller.
        WrapGenerate: func(ctx context.Context, p *ai.GenerateParams, next ai.GenerateNext) (*ai.ModelResponse, error) {
            resp, err := next(ctx, p)
            if err != nil || resp.Text() == "" {
                return resp, err
            }
            verdict, err := gr.classify(ctx, "Does this answer leak private data?", resp.Text())
            if err != nil {
                return nil, err
            }
            if verdict != "ALLOW" {
                return nil, status.Errorf(status.ErrFailedPrecondition,
                    "output guardrail tripped: %s", verdict)
            }
            return resp, nil
        },
    }, nil
}
```

The output hook can also modify or replace the response if desired, as `WrapGenerate` returns the `*ai.ModelResponse` received by the caller.

Similarly, `WrapTool` can intercept tool calls, allowing you to validate or reject arguments before tool execution occurs.

### Plugin-provided middleware and plugin-level state

Middleware shipped as part of a plugin needs two things the simple cases above don't:

1. A way to be **registered automatically** when the plugin is added to `genkit.Init`, so the Dev UI and cross-runtime callers can address it by name.
2. A way to keep **plugin-level state** (an HTTP client, a logger, a database handle) that isn't part of the JSON-serializable config.

Both are handled by implementing `ai.MiddlewarePlugin` on the plugin struct and putting plugin-level state on **unexported fields** of the config struct. The plugin's `Middlewares` method passes a prototype with those fields populated to `ai.NewMiddleware`, which captures it in a build closure. Every JSON-dispatched call, whether from the Dev UI, a `.prompt` file's `use:` entry, or a cross-runtime caller, copies the prototype and decodes its own config over the copy, so unexported state carries into each call and nothing one call sets leaks into the next.

Three rules follow. Exported fields are per-call user config and stay zero on the prototype: a call that omits one gets the zero value, so defaults belong in `New`. State that must be shared across calls, such as a client or a cache, goes behind a pointer, which survives the copy pointing at the same object. And register by value, as below; a pointer prototype is copied through to its pointee, but gains nothing.

```go
import (
    "context"
    "fmt"
    "io"
    "os"
    "time"

    "github.com/firebase/genkit/go/ai"
    "github.com/firebase/genkit/go/core/api"
)

type Logger struct {
    Prefix string    `json:"prefix,omitempty" jsonschema_description:"Text written before each record."`
    out    io.Writer // unexported; preserved across JSON dispatch by value-copy
}

func (Logger) Name() string { return "mine/logger" }

func (l Logger) New(ctx context.Context) (*ai.Hooks, error) {
    out := l.out
    if out == nil {
        out = os.Stderr // a value built outside the plugin has no writer
    }
    return &ai.Hooks{
        WrapModel: func(ctx context.Context, p *ai.ModelParams, next ai.ModelNext) (*ai.ModelResponse, error) {
            start := time.Now()
            resp, err := next(ctx, p)
            fmt.Fprintf(out, "%s model call took %s\n", l.Prefix, time.Since(start))
            return resp, err
        },
    }, nil
}

type LoggerPlugin struct{ Out io.Writer }

func (p *LoggerPlugin) Name() string                          { return "mine/logger" }
func (p *LoggerPlugin) Init(ctx context.Context) []api.Action { return nil }

func (p *LoggerPlugin) Middlewares(ctx context.Context) ([]*ai.MiddlewareDesc, error) {
    return []*ai.MiddlewareDesc{
        ai.NewMiddleware("logs model call latency", Logger{out: p.Out}),
    }, nil
}
```

The `io.Writer` above is the plugin-level state the example is about, not a recommendation: middleware that only wants its records on the trace should call the `core/logger` helpers.

Application code then registers the plugin once during `Init`, which registers the middleware by name:

```go
g := genkit.Init(ctx, genkit.WithPlugins(
    &googlegenai.GoogleAI{},
    &LoggerPlugin{Out: os.Stderr},
))

resp, err := genkit.Generate(ctx, g,
    ai.WithPrompt("Hello"),
    ai.WithUse(Logger{Prefix: "[trace]"}),
)
```

A value passed with `ai.WithUse` runs as you built it, without a registry lookup, so it carries only the fields you set. Code outside the package cannot set `out`, which is why `New` falls back to a default. The prototype applies to calls dispatched by name: when the Dev UI or a `.prompt` file's `use:` entry sends JSON like `{"prefix": "[debug]"}`, Genkit value-copies the prototype to recreate the config, so `out` (which isn't in JSON) comes from the plugin, while the unmarshaled JSON overrides `Prefix`.

The built-in `plugins/middleware` package follows exactly this pattern. See [`plugin.go`](https://github.com/genkit-ai/genkit/blob/main/go/plugins/middleware/plugin.go) for a minimal real-world example.

### Application-owned middleware

When your application code defines a middleware directly rather than wrapping it in a plugin, use `genkit.DefineMiddleware` to register it with the Genkit instance:

```go
genkit.DefineMiddleware(g, "logs model call latency", Logger{out: os.Stderr})
```

Registration surfaces the middleware in the Dev UI and lets cross-runtime callers reference it by name. For pure Go use, registration is not required: passing a middleware value directly to `ai.WithUse` invokes its `New` method on the local fast path. Registration is what makes the middleware visible to the Dev UI.

### Inline middleware

For ad-hoc middleware that doesn't need a named type or Dev UI visibility, use `ai.MiddlewareFunc`:

```go
ai.WithUse(ai.MiddlewareFunc(func(ctx context.Context) (*ai.Hooks, error) {
    return &ai.Hooks{
        WrapModel: func(ctx context.Context, p *ai.ModelParams, next ai.ModelNext) (*ai.ModelResponse, error) {
            logger.Debug(ctx, "model call", "messages", len(p.Request.Messages))
            return next(ctx, p)
        },
    }, nil
}))
```

It works anywhere `ai.WithUse` does: `genkit.Generate`, `Prompt.Execute`, `genkit.DefinePrompt`, and an agent's inline prompt. Inline middleware is resolved on the local fast path and never touches the registry, so every `ai.MiddlewareFunc` shares the placeholder name `inline`.

A closure has no JSON form, so inline middleware lives only in the Go process that created it. Wherever the request is serialized (prompt metadata, trace spans, the Dev UI), it shows as a reference named `inline` with no config, and a request replayed from that JSON, such as a prompt run from the Dev UI, fails with `FAILED_PRECONDITION`. The name `inline` is reserved for this reason. For middleware that must run from JSON, define a named type and register it.

### Composition order

`ai.WithUse(A, B, C)` composes left to right with the first listed middleware as the outermost wrapper, like HTTP middleware: at call time the chain expands to `A { B { C { actual } } }`. Each layer's `next` continuation runs the next inner layer:

```go
ai.WithUse(
    &middleware.Retry{MaxRetries: 3},             // outer: retries the whole inner stack
    &middleware.Fallback{Models: fallbackModels}, // inner: tries fallback models on failure
)
// effective chain: Retry { Fallback { model } }
```

Order matters. `Retry` outside `Fallback` retries the entire fallback cascade as a unit. Swap them and you'd retry the primary first and fall back only after exhausting retries.

For more complex examples of building custom middleware, you can refer to the source code of the built-in middleware in the [Genkit GitHub repository](https://github.com/genkit-ai/genkit/tree/main/go/plugins/middleware).

## Available middleware

The `genkit-middleware` package provides several useful middleware options out of the box.

### 1. FileSystem middleware (`Filesystem`)

Grants the model access to a root directory by injecting `list_files` and
`read_file`. When `allow_write_access=True` (default `False`), it also injects
`write_file` and `edit_file`. All paths are restricted to that root.

```python
from genkit import Genkit
from genkit_middleware import Filesystem

ai = Genkit(...)

response = await ai.generate(
    model='googleai/gemini-flash-latest',
    prompt='Create a hello world node app in the workspace',
    use=[
        Filesystem(root_dir='./workspace', allow_write_access=True)
    ]
)
```

**Configuration options:**
- `root_dir` (required): The root directory to which all filesystem operations are restricted.
- `allow_write_access` (optional): If `True`, adds write/edit tools (defaults to `False` — read-only).
- `tool_name_prefix` (optional): Prefix to add to the name of the injected tools.

### 2. Skills middleware (`Skills`)

Automatically scans a directory for `SKILL.md` files (and their YAML frontmatter) and injects them into the system prompt. It also provides a `use_skill` tool the model can use to retrieve more specific skills on demand.

```python
from genkit import Genkit
from genkit_middleware import Skills

ai = Genkit(...)

response = await ai.generate(
    prompt='How do I run tests in this repo?',
    use=[
        Skills(skill_paths=['./skills'])
    ]
)
```

**Configuration options:**
- `skill_paths` (optional): Paths to directories containing skills (defaults to `['skills']`).

### 3. Tool approval middleware (`ToolApproval`)

Restricts execution of tools to an approved list. If the model attempts to call an unapproved tool, generation finishes interrupted (`FinishReason.INTERRUPTED`) so you can prompt the user for confirmation before resuming.

```python
from genkit import FinishReason, Genkit, restart_tool
from genkit_middleware import ToolApproval
from pydantic import BaseModel, Field

ai = Genkit(...)


class WriteFileInput(BaseModel):
    path: str = Field(description='File path')
    content: str = Field(description='File contents')


@ai.tool()
async def write_file_tool(input: WriteFileInput) -> str:
    """Write a text file."""
    # Persist input.content to input.path in a real app.
    return f'Wrote {input.path}'


# 1. Initial attempt
response = await ai.generate(
    prompt='write a file',
    tools=[write_file_tool],
    use=[
        ToolApproval(allowed_tools=[])  # Empty list means all tool calls trigger interrupt
    ],
)

if response.finish_reason == FinishReason.INTERRUPTED:
    interrupt = response.interrupts[0]

    # 2. Ask user for approval, then recreate the tool request with approval
    approved_part = restart_tool(
        interrupt=interrupt,
        resumed_metadata={'tool_approved': True},
    )

    # 3. Resume execution
    resumed_response = await ai.generate(
        messages=list(response.messages),
        tools=[write_file_tool],
        use=[
            ToolApproval(allowed_tools=[]),
        ],
        resume_restart=approved_part,
    )
```

**Configuration options:**
- `allowed_tools` (optional): List of approved tool names that can run without interruption.

### 4. Retry middleware (`Retry`)

Automatically retries failed model generations on transient error codes (like `RESOURCE_EXHAUSTED`, `UNAVAILABLE`) using exponential backoff with jitter.

```python
from genkit import Genkit
from genkit_middleware import Retry

ai = Genkit(...)

response = await ai.generate(
    model='googleai/gemini-pro-latest',
    prompt='Heavy reasoning task...',
    use=[
        Retry(
            max_retries=3,
            initial_delay_ms=1000,
            backoff_factor=2.0
        )
    ]
)
```

**Configuration options:**
- `max_retries` (optional): The maximum number of times to retry a failed request (default: 3).
- `statuses` (optional): An array of status names that should trigger a retry (default: `['UNAVAILABLE', 'DEADLINE_EXCEEDED', 'RESOURCE_EXHAUSTED', 'ABORTED', 'INTERNAL']`).
- `initial_delay_ms` (optional): The initial delay between retries in milliseconds (default: 1000).
- `max_delay_ms` (optional): The maximum delay between retries in milliseconds (default: 60000).
- `backoff_factor` (optional): The factor by which the delay increases after each retry (exponential backoff, default: 2.0).
- `no_jitter` (optional): Whether to disable jitter on the delay (default: `False`).

### 5. Fallback middleware (`Fallback`)

Automatically switches to a different model if the primary model fails on a specific set of error codes. Useful for falling back to a smaller/faster model when a large model exceeds quota limits.

```python
from genkit import Genkit
from genkit_middleware import Fallback

ai = Genkit(...)

response = await ai.generate(
    model='googleai/gemini-pro-latest',
    prompt='Try the pro model first...',
    use=[
        Fallback(
            models=['googleai/gemini-flash-latest'], # try flash if pro fails
            statuses=['RESOURCE_EXHAUSTED']
        )
    ]
)
```

**Configuration options:**
- `models` (required): A list of model names to try in order.
- `statuses` (optional): A list of status names that should trigger a fallback (default: `['UNAVAILABLE', 'DEADLINE_EXCEEDED', 'RESOURCE_EXHAUSTED', 'ABORTED', 'INTERNAL', 'NOT_FOUND', 'UNIMPLEMENTED']`).

## Building your own custom middleware

You can implement your own custom middleware to extend Genkit's functionality by subclassing `BaseMiddleware`. Registering your subclass with the `@ai.middleware` decorator registers it on the registry so it displays in the Developer UI.

Middleware can intercept different phases of execution by overriding these hooks:
- `wrap_generate`: Intercepts the high-level generation loop.
- `wrap_model`: Intercepts the call to the model.
- `wrap_tool`: Intercepts tool execution.

Here is an example of a custom middleware that logs requests and responses:

```python
from pydantic import BaseModel
from genkit import Genkit
from genkit.middleware import BaseMiddleware, GenerateMiddlewareContext, ModelHookParams

ai = Genkit()

class LoggerConfig(BaseModel):
    verbose: bool = False

@ai.middleware(name='logger_middleware')
class LoggerMiddleware(BaseMiddleware[LoggerConfig]):
    """Logs requests and responses"""

    async def wrap_model(self, params: ModelHookParams, ctx: GenerateMiddlewareContext, next_fn):
        if self.config.verbose:
            print(f"Request: {params.request}")
        
        resp = await next_fn(params, ctx)
        
        if self.config.verbose:
            print(f"Response: {resp}")
        
        return resp
```

To use it:

```python
response = await ai.generate(
    model='googleai/gemini-flash-latest',
    prompt='Hello',
    use=[LoggerMiddleware(verbose=True)],
)
```

For more complex examples of building custom middleware, you can refer to the source code of the built-in middleware in the [Genkit GitHub repository](https://github.com/genkit-ai/genkit/tree/main/py/packages/genkit-middleware).

## Middleware in Dart

Genkit Dart uses a **registry-based system** for middleware, similar to plugins. This allows middleware to be resolved by name and configured via schemas, enabling support for the Genkit Developer UI.

## Available middleware

`retry` and `simulateConstrainedGeneration` are built into `package:genkit` and need no setup. The `filesystem`, `skills`, and `toolApproval` middleware come from the [`genkit_middleware`](https://pub.dev/packages/genkit_middleware) package; register their plugins on the `Genkit` instance so the references resolve:

```dart
import 'package:genkit/genkit.dart';
import 'package:genkit_google_genai/genkit_google_genai.dart';
import 'package:genkit_middleware/genkit_middleware.dart';

final ai = Genkit(
  plugins: [
    googleAI(),
    FilesystemPlugin(),
    SkillsPlugin(),
    ToolApprovalPlugin(),
  ],
);
```

### 1. FileSystem middleware (`filesystem`)

Grants the model access to the local filesystem by injecting standard file manipulation tools (`list_files`, `read_file`, `write_file`, `search_and_replace`). All operations are safely restricted to a specified root directory.

```dart
final response = await ai.generate(
  model: googleAI.gemini('gemini-flash-latest'),
  prompt: 'Create a hello world node app in the workspace',
  use: [
    filesystem(rootDirectory: './workspace'),
  ],
);
```

**Configuration options:**

- `rootDirectory` (required): The root directory to which all filesystem operations are restricted.

_Note: Unlike the JavaScript version, the Dart FileSystem middleware does not currently support `allowWriteAccess` or `toolNamePrefix` options and always enables write operations._

### 2. Skills middleware (`skills`)

Automatically scans a directory for `SKILL.md` files and injects them into the system prompt. It also provides a `use_skill` tool the model can use to retrieve more specific skills on demand.

```dart
final response = await ai.generate(
  prompt: 'How do I run tests in this repo?',
  use: [
    skills(skillPaths: ['./skills']),
  ],
);
```

**Configuration options:**

- `skillPaths` (optional): Paths to directories containing skills (defaults to `['skills']`).

### 3. Tool approval middleware (`toolApproval`)

Restricts execution of tools to an approved list. If the model calls a tool that isn't on the list, the generation stops with `FinishReason.interrupted` so you can ask the user for confirmation before resuming.

```dart
final response = await ai.generate(
  prompt: 'write a file',
  tools: [writeFileTool],
  use: [
    toolApproval(approved: []), // Empty list: every tool call needs approval
  ],
);

if (response.finishReason == FinishReason.interrupted) {
  final interrupt = response.interrupts.first;

  // Ask user for approval...
  final approved = await askUser(interrupt.toolRequest.name);

  if (approved) {
    // Restart the tool call, marked as approved
    final response2 = await ai.generate(
      messages: response.messages,
      tools: [writeFileTool],
      interruptRestart: [
        interrupt.restart({'tool-approved': true}),
      ],
      use: [
        toolApproval(approved: []),
      ],
    );
  }
}
```

**Configuration options:**

- `approved` (optional): List of approved tool names. Replaces the default list set with `ToolApprovalPlugin(approvedTools: [...])`.

### 4. Retry middleware (`retry`)

Automatically retries failed model generations on transient error codes (like `resourceExhausted`, `unavailable`) using exponential backoff with jitter. It is built into `package:genkit`, so there is no plugin to register.

```dart
import 'package:genkit/genkit.dart';

final response = await ai.generate(
  model: googleAI.gemini('gemini-flash-latest'),
  prompt: 'Reliable request',
  use: [
    retry(
      maxRetries: 3,
      initialDelay: const Duration(milliseconds: 500),
      maxDelay: const Duration(seconds: 30),
    ),
  ],
);
```

**Configuration options:**

- `maxRetries` (optional): Maximum number of retry attempts (default: 3).
- `statuses` (optional): A list of `StatusCode` values that should trigger a retry. Defaults to `unavailable`, `deadlineExceeded`, `resourceExhausted`, `aborted`, `internal`.
- `initialDelay` (optional): The delay before the first retry, as a `Duration` (default: 1 second).
- `maxDelay` (optional): The maximum capped delay between retries, as a `Duration` (default: 1 minute).
- `backoffFactor` (optional): Exponential backoff multiplier (default: 2.0).
- `noJitter` (optional): Set to `true` to disable the random factor (Full Jitter) added to the delay (default: false).
- `noRetryModel` (optional): Set to `true` to skip retrying model calls (default: false).
- `retryTools` (optional): Whether to retry tool calls (default: false).

_Note: The `onError` callback is available when instantiating `RetryMiddleware` directly, but cannot be passed via the `retry()` helper._

### 5. Simulated constrained generation (`simulateConstrainedGeneration`)

With an `outputSchema`, Genkit asks the model for native constrained output. For a model or provider without native support, `simulateConstrainedGeneration()` puts the schema in the prompt instead. Nothing enforces the schema, so expect the occasional malformed reply.

```dart
final response = await ai.generate(
  model: myModel,
  prompt: 'Generate a person named John Doe, age 30',
  outputSchema: Person.$schema,
  use: [simulateConstrainedGeneration()],
);
final person = response.output; // Still typed and parsed
```

## Building your own custom middleware

A custom middleware is a class that extends `GenerateMiddleware`, plus an optional configuration schema. Register it so it can be referenced from `use:` and shows up (and can be configured) in the Developer UI.

### 1. Define the configuration schema

Use the `@Schema()` annotation to define the configuration options for your middleware.

```dart
import 'package:schemantic/schemantic.dart';

part 'logger.g.dart';

@Schema()
abstract class $LoggerOptions {
  bool? get enableColor;
  int? get maxLogLength;
}
```

### 2. Implement the middleware logic

Create a class that extends `GenerateMiddleware` and override the hooks you need (`model`, `tool`, or `generate`).

```dart
class LoggerMiddleware extends GenerateMiddleware {
  final bool enableColor;
  final int maxLogLength;

  LoggerMiddleware({
    this.enableColor = false,
    this.maxLogLength = 1000,
  });

  @override
  Future<ModelResponse> model(
    ModelRequest request,
    ActionFnArg<ModelResponseChunk, ModelRequest, void> ctx,
    Future<ModelResponse> Function(
      ModelRequest request,
      ActionFnArg<ModelResponseChunk, ModelRequest, void> ctx,
    ) next,
  ) async {
    // Custom interception logic here...
    return next(request, ctx);
  }
}
```

### 3. Register the middleware

In app code, `ai.defineGenerateMiddleware` registers the middleware and returns its definition. Call the definition to build a reference for `use:`. The `create` callback receives the resolved `config` and a `GenerateMiddlewareContext` (`ctx`), and runs once per `generate` call.

```dart
final logger = ai.defineGenerateMiddleware<LoggerOptions>(
  name: 'logger',
  configSchema: LoggerOptions.$schema,
  create: (config, ctx) => LoggerMiddleware(
    enableColor: config?.enableColor ?? false,
    maxLogLength: config?.maxLogLength ?? 1000,
  ),
);

final response = await ai.generate(
  model: googleAI.gemini('gemini-flash-latest'),
  prompt: 'Hello world',
  use: [
    logger(LoggerOptions(enableColor: true, maxLogLength: 500)),
    retry(maxRetries: 2),
  ],
);
```

The `ctx` argument carries an ephemeral `GenkitAI` instance (`ctx.ai`) backed by the active registry. This lets a middleware run its own AI operations (`generate`, `generateStream`, `embed`) and resolve other registered actions at request time, which is useful for building guardrails, classifiers, or routers. For example, a safety middleware can screen a request with the model before letting it proceed:

```dart
class SafetyMiddleware extends GenerateMiddleware {
  final GenkitAI ai;

  SafetyMiddleware(this.ai);

  @override
  Future<GenerateResult> generate(
    GenerateTurnState envelope,
    ActionFnArg<ModelResponseChunk, GenerateActionOptions, void> ctx,
    Future<GenerateResult> Function(
      GenerateTurnState envelope,
      ActionFnArg<ModelResponseChunk, GenerateActionOptions, void> ctx,
    ) next,
  ) async {
    // Use the ephemeral GenkitAI to classify the request before proceeding.
    final verdict = await ai.generate(
      prompt: 'Reply "block" if this request is unsafe, otherwise "allow": '
          '${envelope.request.messages.last.text}',
    );
    if (verdict.text.trim().toLowerCase().startsWith('block')) {
      throw GenkitException('Request blocked by safety middleware.');
    }
    return next(envelope, ctx);
  }
}

final safety = ai.defineGenerateMiddleware<void>(
  name: 'safety',
  // `ctx.ai` is an ephemeral GenkitAI the middleware can use for its own
  // generate/embed calls at request time.
  create: (config, ctx) => SafetyMiddleware(ctx.ai),
);

// use: [safety()]
```

### 4. Package it in a plugin

To share a middleware across apps or publish it, build the definition with `generateMiddleware` (it doesn't register anything by itself) and return it from a `GenkitPlugin`. A small helper with named parameters makes it pleasant to use:

```dart
final loggerDef = generateMiddleware<LoggerOptions>(
  // The name should be reasonably unique to avoid conflicts with other plugins.
  name: 'logger',
  configSchema: LoggerOptions.$schema,
  create: (config, ctx) => LoggerMiddleware(
    enableColor: config?.enableColor ?? false,
    maxLogLength: config?.maxLogLength ?? 1000,
  ),
);

class LoggerPlugin extends GenkitPlugin {
  @override
  String get name => 'logger';

  @override
  List<GenerateMiddlewareDef> middleware() => [loggerDef];
}

GenerateMiddlewareRef<LoggerOptions> logger({
  bool? enableColor,
  int? maxLogLength,
}) => loggerDef(
  LoggerOptions(enableColor: enableColor, maxLogLength: maxLogLength),
);
```

Users register the plugin and reference the middleware through the helper:

```dart
final ai = Genkit(plugins: [googleAI(), LoggerPlugin()]);

final response = await ai.generate(
  model: googleAI.gemini('gemini-flash-latest'),
  prompt: 'Hello world',
  use: [logger(enableColor: true, maxLogLength: 500)],
);
```

For more complex examples of building custom middleware, you can refer to the source code of the built-in middleware in the [Genkit Dart GitHub repository](https://github.com/genkit-ai/genkit-dart/tree/main/packages/genkit_middleware).
